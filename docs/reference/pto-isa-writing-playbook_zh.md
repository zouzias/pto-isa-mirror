# PTO ISA 写作手册

这份手册面向维护 PTO 架构手册及相关高层文档的作者。

## 优秀的 PTO 文档应该是什么感觉

优秀的 PTO 文档应该像一位有经验的工程师在清楚地解释一个系统，而不是像把术语表强行扩写成完整句子。读者应该能学到：

- 模型是什么
- PTO 为什么这样设计
- 硬边界在哪里
- 哪些行为是可移植的，哪些不是

手册可以带有权威感，但不应该显得匿名、机械。

## 主要写作规则

### 先解释，再归一化

不要在一章开头就先写“范围 / 受众 / 术语”，除非读者真的无法继续。先回答这一章要解决什么问题。

### 谨慎使用规范性术语

只有当一个说法能够被 verifier、backend、测试或评审检查时，才使用 `MUST`、`MUST NOT`、`SHOULD`、`MAY`。不要把它们用于风格偏好、设计哲学或路线图描述。

### 始终给出一个具体例子

每个主要手册章节都应该至少包含一个来自本仓库的例子。优先来源：

- `docs/coding/tutorials/`
- `tests/cpu/st/testcase/`
- `demos/`

例子不需要很大，但必须能把抽象概念落到实际代码上。

### 回答“为什么不是另一种方案？”

当章节引入 PTO 特有概念时，例如 valid region、location intent、显式同步，要顺手回答那个最自然的替代方案。比如：

- 为什么不是通用的 thread-centric 模型？
- 为什么不在 lowering 之后再推断 tile role？
- 为什么不把 backend 行为默认为架构定义？

这是让手册听起来“像作者在讲系统”，而不是“像模板在堆术语”的最简单方式之一。

### 解释性内容优先使用自然段

枚举、矩阵、检查表可以用 bullet。解释应该尽量用自然段。如果一整章几乎全是 bullet，通常意味着作者列出了事实，却没有真正把模型讲清楚。

## PTO 特定的 Do / Don't

Do：

- 在正式规则前，先用自然语言说明架构可见行为
- 明确区分 architecture-defined、implementation-defined、unspecified 和 illegal
- 尽可能把结论连接到仓库中的真实材料
- 保持中英文版本在例子选择和结构上的同步

Don't：

- 当可以直接说明时，用“架构级契约”之类抽象短语掩盖重要语义
- 把写作偏好包装成规范性要求
- 机械地重复同一套章节骨架
- 以“双语翻译”为理由写出不自然的句子

## 推荐的章节形态

对于高层 manual 章节，推荐按下面顺序组织：

1. 这一章回答什么问题
2. 这个主题为什么在 PTO 里重要
3. 一个具体例子
4. 用自然段解释核心概念
5. 规范契约
6. 可移植性或 backend 差异说明
7. 常见误区

不是每章都必须显式写出这些标题，但这些信息都应该被覆盖到。

## 双语策略

英文是 manual 的结构源，但中文不是逐句直译目标。中文版本应当保持含义、例子和边界一致，同时让技术读者读起来是自然的中文。

规则：

- 保持中英文章节顺序一致
- 保持例子选择一致
- 保持关键术语稳定
- 为自然表达重写，而不是机械镜像英文句式

## 评审前自检问题

在合入文档修改前，先问：

- 这一章是在讲清模型，还是只是在定义术语？
- 每一个 `MUST/SHOULD/MAY` 都真的可测吗？
- 是否至少有一个具体例子？
- backend-defined 的边界是否明确写出来了？
- 一个新的 PTO 工程师不额外打开五个页面，也能理解这一章最核心的边界吗？
