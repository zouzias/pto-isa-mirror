# rms_norm — RMSNorm along HEAD_DIM

Auto-mode A3 **vector** kernel that applies `RMSNorm` to the compressed
KV in the [Compressor](../README.md):

```python
# model.py:184-197 (RMSNorm) + model.py:363 (call site)
var = x.square().mean(-1, keepdim=True)
x   = x * torch.rsqrt(var + self.eps)
out = self.weight * x
```

Called as `kv = self.norm(kv_comp.to(dtype))` (model.py:363), so the
input is the output of [c_comp](../c_comp/) (shape `(B, SB, HEAD_DIM)` —
**not** `(B, SB, COFF*HEAD_DIM)`, because by the time `self.norm` runs the
overlap split has already been resolved upstream).

## Reference (CUDA / TileLang)

[deepseek/kernel.py](../../../../../../../deepseek/kernel.py) does not
define a separate RMSNorm kernel; it is the plain PyTorch `RMSNorm.forward`
(model.py:192-197).

## I/O

| Name | Shape | dtype | Source line |
|------|-------|-------|-------------|
| `x`      | `(B, SB, HEAD_DIM)` | FP32 | model.py:194 (`x = x.float()` inside RMSNorm) |
| `weight` | `(HEAD_DIM,)`       | FP32 | model.py:190 (`self.weight`) |
| `out`    | `(B, SB, HEAD_DIM)` | FP32 | model.py:197 (`(self.weight * x).to(dtype)`) |

`eps = 1e-6` (ModelArgs.norm_eps).
`SB = S / compress_ratio`. `HEAD_DIM` is `kCompHeadDim` from the family
manifest (NOT `COFF*HEAD_DIM` — see notes above).

## Memory-budget-first plan

Per [CLAUDE.md §Memory-budget-first kernel planning](../../../../../../../CLAUDE.md):

```text
Memory budgets:
- L1 custom budget:    not used (vector path)
- L0A custom budget:   N/A
- L0B custom budget:   N/A
- L0C custom budget:   N/A
- UB custom budget:    one [HEAD_DIM] FP32 row + one [1] FP32 var scratch
                       + one [HEAD_DIM] FP32 weight (held once) — target ≤ 64 KB

Live tiles by memory level:
- UB:  RowTile (FP32, HEAD_DIM), WeightTile (FP32, HEAD_DIM, reused),
       VarScratch (FP32, 1), RsqrtScratch (FP32, 1)

Smallest hardware operation:
- cube operation shape: N/A
- vector operation shape: 256-byte lane (FP32 → 64 lanes) per VEC issue
  (Assumption — same baseline as add_tile_array)

Loop tiling plan:
- tile-and-loop dimensions: outer loop over (b, sb); inner reduces a
  single (HEAD_DIM,) row. With model defaults HEAD_DIM=512.
- inferred tile sizes: one (b, sb) row per iteration; working set
  3 * HEAD_DIM * 4 ≈ 6 KB.
- compile-time unroll/peel strategy: none for prototype
- tail handling only where needed: HEAD_DIM is typically a power of two;
  no expected tail. Outer B*SB tail handled by valid-region.

Test-shape plan:
- tiny debug shape:        B=1, SB=4,  HEAD_DIM=64
- medium tiling shape:     B=1, SB=32, HEAD_DIM=256
- model-inspired realistic: B=1, SB=64, HEAD_DIM=512 (default)
- tail shape:              N/A
```

## Auto-mode constraints

- A3 only; vector path: `--cce-aicore-arch=dav-c220-vec` (see [CMakeLists.txt](CMakeLists.txt)).
- Single AICORE. No `block_idx` work split.
- No `TASSIGN`, `TPipe`, `TPUSH`/`TPOP`, no raw `set_flag`/`wait_flag`.
- Reduction `mean(x^2)` along HEAD_DIM uses sanctioned `TReduceSum` then
  scalar divide by HEAD_DIM (or `TReduceMean` if available); see
  [docs_for_ai/auto_mode_bad_patterns.md](../../../../../../../docs_for_ai/auto_mode_bad_patterns.md).
- `rsqrt` is a scalar-on-UB op; should fall under the sanctioned vector
  unary ops.

## Comparison policy

- Tolerance-based: relative ≤ `1e-3`, absolute ≤ `1e-4` on FP32 output.
  Mean-square reduction over HEAD_DIM≤512 plus an `rsqrt` ULP — stays well
  inside FP32 tolerance.

## Status

- `Known`: shape and op definition match RMSNorm.forward (model.py:192-197)
  and the call site in Compressor.forward (model.py:363).
- `Known`: `eps = 1e-6` is the ModelArgs.norm_eps default.
- `Assumption`: input shape is `(B, SB, HEAD_DIM)` (not `COFF*HEAD_DIM`).
  In the full Compressor pipeline, `c_comp` is followed by an overlap
  split that drops the COFF axis before `self.norm`. Since this prototype
  ships `c_comp` without that split, the upstream wiring step (when added)
  must insert the split before calling rms_norm — or rms_norm must be
  reshaped accordingly.
- `Unknown` whether this builds — kernel body is a pseudocode skeleton, not
  a real implementation. **No claim of compile / run success** until the
  user runs `run.sh` on the compiler server and reports the output.
